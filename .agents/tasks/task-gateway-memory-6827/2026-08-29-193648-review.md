# Bound the embedder's unused per-token scores buffer (#6827)

The in-process embedder builds the vendored `Llama` object with `n_batch` equal to `n_ctx` (2048). The vendored constructor eagerly allocates `self.scores` as an `(n_batch, n_vocab)` float32 array at model load — for the shipped Qwen3-Embedding-0.6B (`n_vocab` 151,936) that is ~1.24 GB — and the embedding read path never touches it. The change introduces `_N_BATCH = 1_536` and passes it as `n_batch`, shrinking that dead buffer to ~0.93 GB (~311 MB reclaimed) while leaving `n_ctx` and `n_ubatch` untouched so accepted context, micro-batching, and the produced vectors are unchanged. A unit test pins the reduced `n_batch` against the constructor kwargs, and an investigation doc records what was proven from source versus what still needs a live repro.

**Watch for:** the byte-identical guarantee rests on the assumption that a 6000-char input never tokenizes to more than 1536 tokens; the safety margin over the code's own ~4-chars/token estimate (1500) is only 36 tokens, and dense content can tokenize below 4 chars/token (**likely**). This is a defensive baseline fix, not a proven fix for the full 3 GB climb — the doc is explicit about that (**confirmed**).

**Verdict**: APPROVED

## High-level view

The fix is a single call-site lever: `n_batch` moves from `_N_CTX` to a new `_N_BATCH = 1_536`, and because the vendored scores buffer is sized `(n_batch, n_vocab)` when `logits_all` is false at construction, this proportionally shrinks a ~1.24 GB allocation the embedding path never reads. The value 1536 is chosen as the smallest multiple of `_N_UBATCH` (512) that clears the ~1500-token ceiling of a `_MAX_EMBED_CHARS`-clipped input, stays below `n_ctx`, and preserves llama.cpp's `n_batch >= n_ubatch` rule.

The byte-identical claim hinges on `embed(truncate=True)` clipping each input to `n_batch` tokens: as long as no single clipped input exceeds 1536 tokens, last-token pooling reads the same final token and the vector is unchanged. The only pre-Llama guard in `embeddings.py` is a 6000-character clip; there is no token-level check, so the guarantee reduces to the ~4-chars/token heuristic holding for all real inputs. The 36-token margin is the soft spot.

The test suite fakes the vendored `Llama` to capture constructor kwargs and asserts the reduced `n_batch`, unchanged `n_ctx`/`n_ubatch`, coverage of `_MAX_EMBED_CHARS//4` tokens, and a bounded emulated element count. It guards against a revert to `n_batch == n_ctx` but does not exercise real tokenization, so the margin concern is outside its reach. The vendored file is untouched; the embedder is the only in-repo constructor of that class.

### Why 1536 and not the micro-batch

The tempting reduction is `n_batch = _N_UBATCH = 512`, which would cut the buffer to ~310 MB. That is unsafe: `embed(truncate=True)` (vendored `llama.py` ~1145) clips each input to `n_batch` tokens before decode, and knowledge chunks run `CHUNK_TOKEN_SIZE + CHUNK_OVERLAP = 800 + 200 = ~1000` tokens, so 512 would truncate ordinary chunks and, under last-token pooling, change their vectors. Picking 1536 as `3 * _N_UBATCH` keeps `n_batch >= n_ubatch`, stays strictly below `n_ctx` so the buffer shrinks, and clears the ~1500-token ceiling.

The ceiling itself is derived from `_MAX_EMBED_CHARS // 4 = 1500`, an estimate rather than a measured bound. `embeddings.py` clips inputs to 6000 characters (~line 1596) and never tokenizes before handing off, so nothing enforces that 6000 chars stays under 1536 tokens. English prose averages well above 4 chars/token, but source code, dense punctuation, CJK, and whitespace-heavy content routinely tokenize below it. When a 6000-char input crosses 1536 tokens, `embed(truncate=True)` drops the tail and the last-token-pooled vector shifts — exactly the byte-identical property the change advertises. The 36-token margin is the whole safety buffer. Lowering `_MAX_EMBED_CHARS` to a value whose //4 leaves real headroom, or noting explicitly that inputs are assumed never to breach ~4 chars/token, would make the invariant robust rather than probabilistic.

### Buffer sizing and the constructor path

The scores buffer is sized off the raw `n_batch` argument (`llama.py` line 478: `(n_ctx if logits_all == True else n_batch, self._n_vocab)`), with `logits_all` false at construction. Because `_N_BATCH = 1536 < n_ctx = 2048`, the `self.n_batch = min(n_ctx, n_batch)` normalization (line 304) leaves 1536 intact, so the buffer size and the `embed()` truncation ceiling use the same 1536 — a consistency worth noting, since a value above `n_ctx` would have desynced them. The `logits_all = True` inside `embed()` (~line 1088) is a local output-marking flag, not the constructor arg, so the buffer stays dead weight on the read path. A repo-wide grep confirms the embedder is the sole in-repo constructor, so the call-site argument avoids touching the vendored patch.

### Test coverage

The four tests fake the vendored class as the existing embedding tests do, capture the constructor kwargs, and assert the reduced `n_batch`, `n_batch < n_ctx`, unchanged `n_ctx`/`n_ubatch`, `n_batch >= _MAX_EMBED_CHARS//4`, `n_batch >= n_ubatch`, and a bounded emulated `(n_batch, n_vocab)` element count under 1 GiB. Reverting the fix to `n_batch = _N_CTX` fails two of them (`test_embedder_passes_reduced_n_batch` and `test_scores_buffer_element_count_is_bounded`, the latter on `reduced_elems < old_elems` collapsing to equality) — verified in the FEAT-001 scratch harness (4 passed clean, 2 failed on revert).

Not tested: real tokenization near the truncation boundary. Every token-related assertion is arithmetic on constants, so the margin between `_MAX_EMBED_CHARS//4` and `_N_BATCH` is checked as `1500 <= 1536`, not by feeding a dense 6000-char input through a tokenizer and confirming it stays under 1536. A future `_MAX_EMBED_CHARS` increase or a model swap to a denser tokenizer would keep all four tests green while silently breaking vector stability. The live 3 GB symptom is unreproducible in-sandbox, which the doc states plainly; that is an environment limit, not a test gap.

### Investigation doc

The doc separates proven-from-source (buffer exists, fix shrinks it, vectors identical up to the char clip) from unproven (that this fully resolves the 3 GB climb), ruling out five alternative leads with specific file/line citations and deferring the subprocess fan-out to #3259. It gives the reporter a concrete `memory.embedding_provider=""` diagnostic to split embedder baseline from any residual leak.
