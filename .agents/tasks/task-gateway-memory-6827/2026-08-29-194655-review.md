# Enforce the embed char-clip / token / n_batch invariant (v2)

The follow-up commit `e4d1ce2d5` addresses both non-blocking concerns from the v1 review of the scores-buffer fix. The thin 36-token margin behind the byte-identical claim is replaced by an explicit, import-time-enforced relationship: a new `_MIN_CHARS_PER_TOKEN = 3.0` pessimistic floor plus four `assert`s tying `_MAX_EMBED_CHARS`, `_N_BATCH`, `_N_CTX`, and `_N_UBATCH` together so a future constant edit fails fast at import instead of silently truncating and shifting last-token-pooled vectors. The v1 test's constant-arithmetic gap is closed by four new tests that drive a boundary-length input through a floor-density fake tokenizer and a faithful re-implementation of the vendored `embed(truncate=True)` handling. No embedding vectors change: `_N_BATCH` stays 1536, `n_ctx` and `n_ubatch` are untouched.

**Watch for:** the new correctness guard is built on `assert`, which is compiled out under `python -O` / `PYTHONOPTIMIZE`; this repo elsewhere deliberately avoids `assert` for runtime guards for exactly that reason, so the import-time protection silently disappears in an optimized build (**likely**). The `_MIN_CHARS_PER_TOKEN = 3.0` floor is validated against the shipped Qwen3 tokenizer only; a config-substituted custom model with a denser tokenizer would violate the assumption while the constant-based asserts still pass (**possible**).

**Verdict**: APPROVED

## High-level view

Both v1 concerns are resolved. Concern #1 (probabilistic ~4-chars/token assumption with a 36-token margin) is now an explicit invariant: `_MIN_CHARS_PER_TOKEN = 3.0` is a deliberately pessimistic floor, and the hard bound `_MAX_EMBED_CHARS / _MIN_CHARS_PER_TOKEN <= _N_CTX` (2000 ≤ 2048) guarantees even a pathological clipped blob still decodes. The comment block scopes byte-identity honestly: unconditional for the inputs the system actually produces (chunks ~1000 tokens, memories ~500, both well under `_N_BATCH`), while a 6000-char single blob is an already-degraded truncated path that was never promised byte-identity.

Concern #2 is resolved by four tests that stop asserting arithmetic on the same constants and instead pin the floor as genuinely pessimistic (`< 4.0`), tokenize a real max-length blob at the floor density, and run it through a re-implementation of `embed(truncate=True)` that matches the vendored `tokens[:n_batch]` + overrun-check logic. These fail if `_MAX_EMBED_CHARS` is bumped, `_N_BATCH` shrunk, or the floor raised — the exact regressions the invariant guards.

The enforcement mechanism carries the only residual note. The four `assert`s operate purely on module-level literals — none of `_MAX_EMBED_CHARS`, `_N_CTX`, `_N_BATCH`, `_N_UBATCH` is config- or env-overridable, so they cannot spuriously fire for any legitimate deployment; they bite only on a source edit, which is the intent. But `assert` is stripped under `python -O`, and this codebase explicitly rejects `assert` for runtime guards in at least three other places, so the guard is convention-inconsistent and vanishes in an optimized interpreter.

### The invariant replaces the margin, and it is honestly scoped

The v1 discomfort was that `n_batch=1536` sat only 36 tokens above the `_MAX_EMBED_CHARS//4 = 1500` estimate with no token-level bound before Llama. The hard bound `_MAX_EMBED_CHARS / _MIN_CHARS_PER_TOKEN <= _N_CTX` (6000/3.0 = 2000 ≤ 2048) is now a real guarantee: at the pessimistic floor, even a fully-clipped pathological blob decodes without overrunning the context window. The byte-identity bound is separated out and stated plainly — a 2000-token pathological blob *does* exceed `_N_BATCH` (1536) and *would* be truncated, but that path is already degraded and was never promised byte-identity. Real inputs (chunker `800+200 ≈ 1000` tokens, memories `~500`) sit ~500 tokens under `_N_BATCH`, so their vectors are unconditionally stable.

`_N_BATCH >= _MAX_EMBED_CHARS // 4` keeps the nominal ~4-char/token ceiling as a headroom floor, so a future `_N_BATCH` reduction below 1500 fails at import. The remaining two asserts (`_N_BATCH < _N_CTX`, `_N_BATCH >= _N_UBATCH`) promote the previously-commented buffer-bounding and llama.cpp constraints into enforced checks.

### The `-O` gap in the enforcement mechanism

Under `python -O` or `PYTHONOPTIMIZE=1`, all four `assert` statements are removed from the bytecode, so an optimized build loses the fail-fast protection entirely — a bad constant edit would then ship silently, exactly the outcome the follow-up set out to prevent. This is not hypothetical for this codebase: three other sites explicitly comment that they avoid `assert` because "asserts vanish under `python -O`" (`builtin_skills/goal-conductor/scripts/ledger_entry.py:358`, `dashboard/ws_event_scope.py:476`, and the matching test). No `-O` invocation appears in the build or run scripts today, which keeps this non-blocking — but an explicit `raise` would align with the repo's own pattern and be robust regardless of interpreter flags.

### The asserts run on fixed literals, not config

An import-time assert on a config-overridable value would be a real hazard, so it is worth ruling out. `_MAX_EMBED_CHARS`, `_N_CTX`, `_N_BATCH`, and `_N_UBATCH` are module-level literals passed directly into the `Llama` constructor (`embeddings.py:1413-1422`) and into the char clip (`:1655-1657`); no config key, env var, or runtime path rewrites any of them. The overridable surface is the model *path* and *URL* only, so the asserts evaluate to a fixed truth for every deployment and can trip solely on a source edit.

The residual is that a custom model swapped in via config could carry a tokenizer denser than the 3.0 floor while `n_batch`/`n_ctx` remain fixed; nothing enforces the floor against the actually-loaded tokenizer, so that case would degrade vectors without any assert firing. The comment designates `_MIN_CHARS_PER_TOKEN` as the single revisit point on a model swap; a token-count check on the post-clip input inside `embed` would be the complete fix if custom models become common.

### Test strengthening drives the boundary it depends on

The four new tests close the v1 gap where every token assertion was arithmetic on the same constants. `test_min_chars_per_token_floor_is_pessimistic` fails if the floor is raised toward 4.0 to make a larger clip "fit" — directly guarding the escape hatch. `test_clipped_input_at_floor_fits_context_without_full_loss` builds a real `_MAX_EMBED_CHARS`-length blob, tokenizes it at the floor density, and runs it through `_simulate_embed_truncation`, whose `tokens[:n_batch]` slice and post-clip overrun check match the vendored `embed(truncate=True)` at `llama.py:1145-1155` exactly. `test_chunked_input_is_never_truncated_at_floor` folds the chunker budget back to characters at the floor and asserts no truncation, so a `_N_BATCH` shrink below the real chunk ceiling breaks a test rather than passing green.

Verified in the FEAT-001 scratch harness (pyenv 3.11.15, `PYTHONPATH=src`, empty conftest, `--confcutdir`): **8 passed** (4 original + 4 new), and `import kiro_crew.embeddings` succeeds with `_N_BATCH=1536`, `_MIN_CHARS_PER_TOKEN=3.0`.

Not tested: real tokenization with the actual Qwen3 tokenizer (environment limit — no model download under INTEGRATIONS_ONLY), and behavior under `python -O` where the import asserts are absent. The first is an accepted constraint; the second is the mechanism concern above.
